# Integration contracts

These pure TypeScript adapters belong to Sermonstudyapp's backend. `index.ts` is the public entrypoint. Runtime dependency: `luxon@3.7.2`; development: `@types/luxon@3.7.6`, existing TypeScript/tsx and Node types. No SDK installation is required. Backend lead owns manifests, HTTP routes, DB transactions, provider activation and workers.

## Evidence and activation

Local tests use `node:test` through `tsx --test tests/integrations/*.test.ts` from backend, with actual HTTP fetch requests to loopback stub servers. The provider API suite additionally uses a uniquely named, isolated real PostgreSQL database. They demonstrate request encoding and local handling, not provider compatibility or account connectivity. No real provider API request, key, account, church data, message or billing operation was used. Official documentation was read before implementation. External proof remains **BLOCKED** pending explicit account authorization, credentials, source/translation rights and church review. Live provider gates cannot be satisfied by these tests. Clearstream and Text In Church are unsupported; Twilio is the implemented candidate, not an activated sender. Configured audio transcription requires an explicitly injected trusted scanner/duration inspector; the environment-only default remains disabled for audio. PDF/DOCX extraction is unsupported; never relabel notes as a complete transcript.

`new OpenAIResponsesAdapter()`, `new PlanningCenterAdapter()` and `new TwilioAdapter()` do not silently read provider credentials or fabricate success. Required credentials/model must be explicitly configured by the application. Missing configuration throws `IntegrationError` with `code=PROVIDER_DISABLED`, `statusCode=503`. `PCO_TOKEN_ENCRYPTION_KEY` is the sole helper environment fallback. All adapters support injected `fetch`, `baseUrl`, `timeoutMs` for local contract tests; application configuration must not expose these overrides to incoming requests. Adapters perform one network attempt and reject redirects. They never log secrets. Errors expose provider status codes without returning raw provider bodies or tokens.

Persist civil intent, resolved UTC, timezone database/runtime version and schedule version. Map API `timeZone` to helper `zone`; an overlap UI's offset choice must become signed integer minutes (New York fall overlap: -240 or -300). Worker derives `approvedAt` and `unchanged` from trusted immutable DB approvals/current dependencies, never request booleans. Helpers do not authorize publishing. Recipient zone source, notification expiry, consent, suppression, sender scope, authorized preview, budgets and dispatch lease remain DB/worker checks immediately before sending. Unknown zone holds without area-code or church-zone guesses; no geographic fallback is implemented. Expiry is the last authorized sending deadline, not permission to send the next morning automatically. Stricter tenant rules remain the caller's responsibility.

## OpenAI proposal adapter

Constructor `new OpenAIResponsesAdapter({apiKey,model,fetch?,baseUrl?,timeoutMs?})`. Methods `proposeWeek`, `proposePlan`, `assistField`, `draftStudy`, `revise` take `Omit<AIRequest,'workflow'>`; general `propose` takes the workflow explicitly. Workflows are `week_outline`, `day_plan`, `field_assistance`, `study_draft`, `revision_help`. Read the exported `AIRequest`, `AISource`, `AIProposal`, `AIProposalField` types. Each input needs an explicit generation action, task, base revision or null, profile/version, selected immutable source revisions/spans and a reserved token budget. Assistance needs `selectedField`, revision help a base revision, week outline 1–7 dates, full drafting an exact approved plan revision. Merely viewing cached suggestions must not call a method.

Six plan fields: `title`, `primaryScripture`, `learningObjective`, `outline`, `discussionQuestion`, `notes`. Full study fields: `title`, `body`, `reflection`, `discussionQuestion`, `application`, `smsPreview`. A study draft includes a complete nonempty devotional body based on the supplied exact approved-plan content; the application worker loads that content from trusted storage. Suggestions are plain text, not domain payload mutations. Backend adoption maps Scripture text into `primaryScripture.reference`, splits/reviews outline text into domain outline items, maps proposed `smsPreview` to content `outboundPreview` and body to `content.body`. Other fields remain untouched during selective adoption. References and approval relationships need explicit contributor/domain handling; do not auto-invent their values. All drafts remain unapproved and must satisfy the unchanged completeness/review checks. Weekly output has one field set per requested date; other workflows use `date:null`.

Model sees fixed instructions, with source/profile/task JSON only in untrusted user content, `tools:[]`, `store:false`, bounded source count/input/output and strict `text.format` JSON schema. Output is validated again locally: exact keys, allowed fields/date coverage, unique field/date pairs, bounded strings, no HTML/HTTP links, known selected source/span IDs, Scripture reference syntax, completed result, refusal handling and usage. Matching source IDs proves attribution only; it does not prove a generated statement follows from the source. Scripture suggestions remain unverified, and a fluent proposal is never doctrinal approval. A hostile transcript can still influence model prose; no tools, credentials or domain privileges are available to it.

Input budget uses a conservative UTF-8 byte upper-bound estimate plus schema/instruction overhead. Workflow caps: week 12k/2k, plan 8k/1.5k, assistance and revision 3k/600, study 10k/2k. Caller must atomically reserve tenant spend/tokens before invocation, prevent simultaneous reservation overspend, and reconcile actual billed usage even on failed/incomplete output. This adapter does not replace a persistent tenant budget ledger. It performs no automatic retries. Output includes provider response/model, prompt/profile version, complete input configuration hash, output/source hashes and usage; do not persist hidden reasoning. Bind creator/request/tenant/adoption audit at the HTTP/domain boundary. Persist proposals separately. Adoption requires current capability, rights, base-head ETag, selected source authorization and human confirmation. Full study route must verify the supplied plan revision is actually approved, not trust the ID's presence. Display plain text or escape it; perform separate link/HTML sanitization if a future UI supports rich text.

## Planning Center read adapter

Constructor accepts `{accessToken?,clientId?,clientSecret?,allowAudioDownload?,fetch?,baseUrl?,timeoutMs?}`. `authorizationUrl({redirectUri,state,codeVerifier})` uses Publishing scope and PKCE S256. Caller generates cryptographically random state/verifier, binds them to session/tenant/connection and expiry, validates callback state exactly once, and allowlists redirect URIs. `exchangeCode`, `refresh`, `revoke` implement OAuth lifecycle. Serialize refresh per connection and atomically replace encrypted access/refresh tokens; never retry code exchange blindly. `revoke(token,tokenType?)` defaults to refresh-token revocation; keep disconnect pending if remote cleanup fails.

`read(path)` permits only Publishing episodes and listed associations, `/current/v2/me`, `/webhooks/v2/available_events`; only `per_page`, `offset`, `include` query keys. `listEpisodes(offset)` requests pages of 100. Follow pagination only through this allowlisted method; do not fetch provider-returned URLs directly with credentials. `availableEvents()` returns actual provider discovery; no event catalog is invented. Optional `generateAudioDownloadUrl(episodeId)` is the only content POST and requires configuration opt-in; its signed URL must pass the media fetch/rights policy separately. Episode/notes mutation and People requests are rejected. OAuth token/revocation operations are separate lifecycle POSTs, not editorial writes. PCO read results are untrusted raw JSON: backend validates schema, confirmed organization binding, selected channel/publication visibility and import mapping before persistence. An absent episode or 404 does not establish deletion.

Use a managed random 32-byte encryption key encoded as canonical base64, supplied via secrets management/`PCO_TOKEN_ENCRYPTION_KEY`. Binding should encode both tenant and connection unambiguously (for example `JSON.stringify([churchId,connectionId])`). Maintain external key IDs for rotation; envelopes are v1 and do not include a key ID. Subscription ID/secret must be obtained from tenant-owned configuration before verifying a webhook. Signature alone provides no replay/freshness guarantee: durably deduplicate subscription/delivery IDs and enqueue before returning HTTP 200; fetch current state rather than trusting event ordering. Expose 429 retry information to the queue; no automatic retry is performed. No ordinary-member Church Center SSO, implicit membership or native external-study publishing is implemented. Current official authentication docs now describe OIDC; this newly observed documentation does not prove ordinary-member handoff and does not activate an identity capability.

## Twilio candidate

Constructor `{accountSid,authToken,from?,messagingServiceSid?,fetch?,baseUrl?,timeoutMs?}`. `send({to,body,statusCallback?})` POSTs URL-encoded form to Messages; `status(sid)` GETs a message and binds returned account/message identity. Return `{provider:'twilio',sid,status,errorCode,evidence:'provider_status_only'}`. `queued` is provider queue evidence, not member receipt/read. No idempotency header or exactly-once claim. Timeout, transport failure, malformed accepted response and 5xx after POST become `SUBMISSION_UNKNOWN`; do not retry until reconciliation establishes non-acceptance or a separately authorized resend acknowledges duplicate risk. 429 exposes retry timing. Caller retains send-intent and callback correlation to reconcile.

Webhook handler must select trusted tenant account/token, retain raw bounded body and exact configured external URL (including query), verify signature before parsing effects, and bind inbound AccountSid/MessageSid/sender to tenant-owned records. Do not derive the signature URL from untrusted forwarded headers. Include every form parameter, including future fields. JSON mode verifies `bodySHA256`. Only form and JSON SMS callback shapes are supported. Credentials-in-URL and URL rewrite variants are not accepted as alternate signatures; configure a canonical external callback URL. Duplicate and out-of-order callback processing belongs in durable DB records; valid signatures alone prove no freshness. STOP and consent projection updates have priority over further dispatch. No carrier registration, permission, consent or delivery proof is inferred from HTTP success.

## Scripture trust boundary

`ScriptureEvidence` must come from a trusted authorized corpus/verifier, not the model or submitted browser JSON. Exact string comparison preserves punctuation and bytes; a missing rights/license record or different edition blocks exact-text verification. Existence is an evidence lookup result, not a regex-based Bible catalog claim. SHA256 authenticates a stored snapshot only relative to its trusted provenance; it does not prove licensing or interpretation. No licensed provider/corpus is configured here, so real Scripture verification remains blocked.

## Official implementation references

Checked 2026-10-18; documentation support only, no live account exercise:

- [OpenAI Structured Outputs for Responses](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses): strict `text.format`, output/refusal handling.
- [Twilio Security](https://www.twilio.com/docs/usage/security): external URL, all form fields, HMAC-SHA1, JSON bodySHA256; SDK verification is recommended by Twilio. This implementation uses Node crypto and regression-tests the official fixed example; real callback acceptance remains a gate.
- [Twilio Messages resource](https://www.twilio.com/docs/messaging/api/message-resource): send/status and status callback contracts.
- [Planning Center authentication](https://api.planningcenteronline.com/docs/overview/authentication): Publishing scope, PKCE, code/refresh/revoke lifecycle; newly documented OIDC does not establish session handoff evidence.
- [Planning Center webhooks](https://api.planningcenteronline.com/docs/overview/webhooks): hexadecimal HMAC-SHA256 over actual raw bytes; delivery retries and HTTP acknowledgements.

Before activation collect authorized provider request/response evidence, current account permissions/organization/event names, OAuth lifecycle and remote disconnect, callback signature round trips and duplicate handling, channel scope, sender registration and STOP behavior, provider privacy/budget controls, source rights/translation license and church-reviewed AI evaluation. Do not mark G2/G3/G4 complete from local test results.

## Application orchestration

The assigned `src/api/provider-routes.ts` plugin and `002_providers.sql` implement source capture/review, durable generation/transcription jobs and budget reservations, proposal inspection/selective adoption through the core immutable-revision service, OAuth encrypted connection lifecycle, bounded selected-channel note reconciliation, verified webhook inboxes, consent/suppression records and SMS intents. See `contracts/PROVIDERS.md` for HTTP and configuration contracts. The app and worker registration are owned by the backend lead. PCO imports require staff-confirmed preached dates and never substitute an import/publication timestamp. Successful token rotation commits independently of subsequent import failure. Final dispatch rechecks active recipient, publisher and both approvers plus exact publication/preview/consent dependencies; no in-flight network recall is promised.

`OpenAITranscriptionAdapter({apiKey,model,...transport}).transcribe(TranscriptionRequest)` posts actual multipart audio to `/v1/audio/transcriptions`, bounded to25MB and a trusted reserved duration. It requires explicit action, rights and trusted scan evidence; it returns an unreviewed normalized transcript/source digest and provider usage. The app persists encrypted quarantined audio only in its pending job and purges that field on finalization. Model compatibility, consented audio accuracy, production scanning/duration inspection, large-file chunking and provider retention remain external/operational gates. [Official file transcription reference](https://developers.openai.com/api/reference/resources/audio/subresources/transcriptions/methods/create).
