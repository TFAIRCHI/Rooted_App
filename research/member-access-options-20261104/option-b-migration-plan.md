# Option B migration plan: from member accounts to public studies

Research snapshot: **2026-11-04**. This is the implementation contract for [Option B](option-b-public-links.md), with the [Twilio owner checklist](option-b-twilio-setup.md) as its external setup companion. It proposes a reversible, staged migration from Rooted's current signed-in member reading and engagement model to publicly readable church studies, anonymous reactions, and named moderated comments. It changes no running application. The [build prompt](../../BuildPrompts/option-b-public-study-migration/MASTER_BUILD_PROMPT.md) translates this plan into implementation work.

## 1. Target contract and explicit decisions

| Question | Decision for this build |
| --- | --- |
| Who reads? | Anyone can open `/c/{churchSlug}` and `/c/{churchSlug}/studies/{publicationId}` without an account. The church page lists all **current, live, published, nonwithdrawn** studies. The URL is stable and shareable. There is no link token, expiry, or phone-based login. |
| Who creates, approves, sends, moderates? | Existing authenticated church contributors and administrators. Keep Entra/OIDC, contributor MFA, tenant checks, capability gates, immutable study review and human approval. |
| What does a recipient get? | A consented scheduled SMS with the registered sender name, a contributor-written short note, study title, canonical public URL and required opt-out text. A click opens that exact study. The SMS is an invitation, not an identity credential. |
| Reactions | No sign-in or name. One selected reaction per study per browser identifier is the product behavior; it cannot prove one reaction per person. Allow change/removal. Counts are reaction events, not unique members. |
| Comments | A name and text are mandatory, but the name is **self-provided and unverified**. New comments enter a pending moderation queue and appear publicly only after approval. Staff replies use authenticated attribution. |
| Historic member discussions | Keep them staff-visible under existing retention controls. Do **not** publish them merely because reading becomes public. The church may later run a separate, consent-reviewed release of selected historical material. |
| Old study links | A live publication keeps its existing publication-ID URL. A withdrawn or superseded publication returns an unavailable state; do not show an old revision or silently map its comments to a new study. |
| Search visibility | Public access is the product contract. Pilot may use `noindex`; this only affects cooperative search engines and is not an access control. Decide lasting indexing policy before broad rollout. [Google Search Central](https://developers.google.com/search/docs/crawling-indexing/block-indexing). |
| Tracking | Keep historical member metrics labeled as **legacy**. New dashboard metrics use aggregate public views, reaction counts and approved/pending comments. Do not show member reach, unique-person percentages, or per-person paths for the public era. |

The phrase “remove member-level access” means readers no longer need Rooted accounts. It does **not** mean dropping `memberships` wholesale: staff capabilities, approvals, moderation actors, audit and privacy records still depend on them. Retire reader-only membership workflows after their data has been accounted for.

Use three church-scoped rollout controls: `public_read_enabled`, `public_engagement_enabled`, and `study_sms_enabled`, all false by default. Store the staff actor and time for the church's public-content review and sender/consent activation. Enforce `public_engagement_enabled` only when both public reading controls are enabled; enforce `study_sms_enabled` only when those controls and a registered sender are active. Existing `reading_policy` continues to gate the current public route during rollout; set it to `public` only when the content review passes and `public_read_enabled` is switched on. **Do not add the new flag as a second gate to the legacy public GET route until any churches already using `reading_policy='public'` have been inventoried and grandfathered or reviewed**; a schema rollout must not unexpectedly hide their published studies. The new engagement/SMS routes always require their own flags. For rollback, turn off SMS intent creation and public writes independently. Do not silently switch reading back to member-only after links have been shared; record that as a church content decision.

## 3. Data migration: additive first, removal last

**First migration (expand):** use the next available sequential SQL migration, not an edited historical file. Create new `public_reactions`, `public_discussions` and `public_discussion_reports` tables with `(church_id, publication_id)` foreign keys, status/version/created timestamps and staff moderation actor references. Public discussion rows have required `display_name` and body, `author_kind` (`visitor|staff`), nullable `staff_user_id`, optional parent for staff replies, and a distinct public visibility status. Keep legacy `discussions`, `reactions`, `reports`, `study_opens` and `publication_audiences` unchanged. Add tenant RLS to all new tables with `FORCE ROW LEVEL SECURITY`; public API handlers must resolve the church from the allowed slug, set `app.church_id` inside a transaction, and query only live publications. Validate that no public route uses a privileged database role or leaks cross-tenant rows.

Add `schedules.reserved_publication_id` (unique within church) and backfill pending schedules with fresh UUIDs. On every new schedule, allocate the ID once and keep it immutable for that schedule. Change `publishOccurrence` to insert the publication using the reserved ID, while preserving its current `(church_id,schedule_id)` idempotence and existing already-published IDs. This is necessary because the current worker generates the ID only at publication time; an SMS containing the exact public URL cannot be approved earlier otherwise. Add `sms_delivery_snapshots` keyed by church/schedule and version with the exact composed body, digest, public URL, sender scope, study revision/approval IDs, creator and reviewer IDs, approval time and segment count. Keep prior snapshots immutable; only one current approved snapshot may drive new intents. Add `sms_snapshot_id` to new send intents while leaving historical intents readable. A study can publish without an SMS snapshot, but it must not silently send a message.

Use a random first-party visitor cookie for reaction update convenience. Store only an HMAC/keyed digest scoped to church and study, with a unique `(church_id, publication_id, visitor_digest)` constraint. Keep the key outside source and images. Rotate/expire identifiers under a documented retention policy; after rotation or cookie loss, counts can increase. Do not fingerprint devices or equate a cookie with a person. Comments may use a separate opaque receipt token if later self-service edit/delete is desired; for the first release, use a church-assisted removal request and avoid promising authenticated ownership. The comment name remains unverified. Public comment reports can be submitted without an account but need bounded text, rate limits and a staff review queue.

**Recipient expansion:** safest path is to keep `provider_contacts` IDs so immutable `provider_consent_events` and `provider_send_intents` continue to point to the same records. Add optional recipient display label/provenance, contact state, consent-audit status and nullable legacy `user_id`; only after read/write code supports independent contacts, drop `user_id NOT NULL` and its mandatory membership FK. Keep `actor_id` on consent events and send intents as authenticated staff audit identity. Preserve encrypted E.164 phone, sender-scoped hash, time zone, consent version and suppression. Any new contact starts suppressed. Backfill existing contacts with their old identifiers and consent events; do not infer new public-link SMS consent from a directory entry. Mark a contact send-eligible only after the church confirms that its recorded consent covers this sender and study-notification purpose. On ambiguous or missing evidence, leave suppressed and obtain fresh opt-in. Do not reset STOP or resubscribe merely because the record was migrated. [Twilio Messaging Policy](https://www.twilio.com/en-us/legal/messaging-policy).

**Sender expansion:** current environment configuration supports one church/sender at a time. For a single-church pilot, retain that scope. Before multiple churches, introduce a tenant-scoped sender registry with church ID, Twilio account/sender identity, approved campaign status, callback signing credential reference, sender scope and activation state. Keep secrets in Azure secret storage; never place them in church-editable records or frontend responses. Route worker jobs and callbacks by trusted church/connection, not caller-supplied identity. Twilio's [ISV onboarding guidance](https://www.twilio.com/docs/messaging/compliance/a2p-10dlc/onboarding-isv) treats client senders as distinct brands/campaigns; sender ownership is a registration decision, not a database default.

**Public exposure review:** inventory every current live publication per church. Record owner approval that its text, embedded source excerpts, title, links and images can be public. Hold the church flag off while reviewing. Do not backfill old member comments into `public_discussions`; private or restricted-audience comments may contain names or personal details. Preserve historical staff access and retention. Update the privacy process for public comments and recipient contacts; because visitors lack accounts, offer an accessible request route and identity/evidence review before disclosing or removing data.

**Final contraction:** only after every intended church has passed the public reader and delivery gates, disable reader-only invitation, onboarding and member sign-in affordances; revoke reader-only sessions; retire their public-facing endpoints; archive/deactivate reader-only memberships according to a retention review. Do not delete any row still referenced by approvals, audit, consent, historic engagement, privacy records or staff activity. Preserve a compatible read path for old records until retention work is complete. Removing `reading_policy='members'` from the schema is optional final cleanup, not a prerequisite for launch.

## 4. API and UI transition contract

### Public reads and participant actions

Use the existing `GET /v1/public/churches/:slug/studies[/:id]` shape for reading, with a shared helper that checks the current live publication and church policy. Add `GET /v1/public/churches/:slug/studies/:id/community` (bounded/paginated), `PUT .../:id/reaction` (`type` from the existing five reaction types or `null`), `POST .../:id/comments` (`displayName`, `body`, `kind=response|question`) and `POST .../:id/reports` (`commentId`, `reason`). Return only approved public comments and staff replies; a submitted comment returns only its receipt/status to that requester, never a publicly guessable pending list. Suggested first-release bounds: 120 characters for a name, 5,000 for a comment, 1,000 for a report; 3 comments and 5 reports per 10 minutes per visitor/network, and a separate reaction-change limit. Make these configurable and test rate limits from a real shared store, not per-process memory. Do not return phone numbers, visitor digests, raw IPs, unapproved text, staff-only notes or legacy member discussions.

Public writes need JSON content-type/body-size limits; exact-origin validation or an equivalent CSRF defense for cookie-bearing requests; first-party `Secure`, `HttpOnly`, `SameSite` cookie settings; input length validation; plain-text rendering; and durable rate limits by coarse IP/network and visitor identifier. Reject cross-origin writes without suitable origin evidence, but allow ordinary anonymous GETs and SMS link previews. Apply abuse controls without making a name or account necessary for reactions. OWASP notes that `SameSite` alone is insufficient as an origin check, including for unauthenticated cookie flows. [OWASP CSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html). Document trusted proxy/IP handling so a client header cannot choose its own rate-limit key.

Keep staff moderator routes authenticated. Show public and legacy comments clearly separated by provenance; allow approve/hide/decline, reports, staff reply and removal requests on the new stream. Ensure old moderation queries that inner-join `memberships` do not silently omit public comments. Continue to honor `discussions_enabled`; public comments are hidden/disabled when it is false, while reading and reactions remain available under the church's policy. If a study is withdrawn, its community writes stop and public read returns unavailable. The existing [tenant route helper](../../backend/src/api/tenant-boundary.ts) authenticates even `access='member'`, so public writes require a deliberately separate handler and transaction path.

On the frontend, keep `/c/:slug` and `/c/:slug/studies/:id` as canonical destinations. Use the public API for reader data whether or not a staff session exists. Show “All available studies,” reaction buttons, a comment form requiring name and body, moderation status copy and an unverified-name label. Provide no reader sign-in prompt. A contributor may still enter the staff workspace via a distinct sign-in action. Replace local-storage completion keys that use member IDs with a browser-local study key or leave completion ephemeral; do not claim cross-device sync. Update `/find-church`, public marketing copy, invitation paths and account navigation to direct readers to church URLs while preserving contributor onboarding and staff invitations.

### SMS composition and scheduling

Add a contributor-written `delivery_note` (initial bound: 240 characters) and a composed preview **separate from untrusted arbitrary URLs**. The server builds the canonical HTTPS URL from configured public origin, church slug and the schedule's reserved publication ID. The creator edits the note while preparing the schedule. Before the due time, an authorized reviewer confirms an immutable SMS snapshot containing the exact note, sender label, title, URL, opt-out line and segment count. A changed study revision, schedule, sender or note invalidates that snapshot and requires fresh review. Keep this SMS approval distinct from the study-content approval; both must be current to send. Use the church's actual registered sender identity and verified consent wording. Do not send a generic Rooted-branded message for a church-registered campaign.

Current `POST /sms/intents` is an explicit staff command and creates intents with immediate `not_before`. At the moment `publishOccurrence` commits the reserved publication ID, enqueue a durable notification event (or create intents transactionally) **only if** a current approved SMS snapshot exists. A worker then creates one intent per consent-audited eligible contact with `not_before` no earlier than publication, expiry **24 hours after publication** for the first release, and a unique publication/contact constraint. If snapshot approval was missed before a timed publication, publish the web study without SMS; staff may perform a separately reviewed late-send action only within those 24 hours. Never synthesize an SMS approval after publication. Serialize or idempotently deduplicate publication/recipient scheduling, including restart/retry. Before each Twilio call, recheck live publication, exact approved message hash, staff authority, recipient consent version, suppression, sender registration/activation, recipient time zone/quiet window and segment budget. Remove only the requirement that recipient have an active Rooted membership. A STOP callback must suppress pending work even after an intent is created; `submission_unknown` must reconcile before any resend. [Twilio Advanced Opt-Out](https://www.twilio.com/docs/messaging/tutorials/advanced-opt-out) can send `OptOutType` to Rooted, but the app must maintain its own suppression state.

Use the current callback URL contract only after confirming the proxy path and signature URL. Do not switch a production Messaging Service webhook until the receiving API revision is deployed and tested. Verify real inbound STOP/HELP and outbound delivery events with a pilot sender; provider acceptance is not proof of handset receipt or study reading.

## 6. Verification matrix

| Scenario | Expected outcome |
| --- | --- |
| Anonymous direct URL, SMS URL, forwarded URL, refresh/new device | Same current study and public library, no sign-in. |
| Draft, future schedule, deleted, withdrawn, superseded publication | No public payload or comments; clear unavailable response. |
| Cross-church publication ID or cross-tenant comment/reaction/report | No data or write; tenant RLS still isolates records. |
| Guest reaction without name; change/remove; cleared cookie or second device | Works without sign-in; counts described as approximate, not unique people. |
| Guest comment missing name; valid comment; pending/approved/hidden | Missing name rejected; valid submission pending; only approved content public; staff can moderate. |
| Old member comment after public switch | Staff can find it, but public API cannot return it. |
| Malicious cross-origin POST, oversized body, burst submissions | Rejected/rate-limited; reading still works. |
| Consent absent, revoked, STOP during queue, unknown recipient time zone | No send; existing suppression and quiet-hour holds remain. |
| Approved note edited, publication withdrawn, sender changed, staff authority revoked | Pending send blocked until new approval/configuration. |
| Worker restart, Twilio timeout or `submission_unknown` | No automatic duplicate message; reconcile provider evidence before resend. |
| Staff account, MFA, review/approval, moderation and privacy requests | Continue through authenticated paths and correct tenant. |
| Old application image against expanded schema | Passes a limited check **before** new independent recipients/intents are created; do not assume old worker can process new rows later. |

Automate focused backend integration tests, a clean and populated database migration test, frontend E2E guest/staff journeys, and local built-image smoke tests. Run actual live Twilio sends only in an approved, consented pilot; use provider stubs for ordinary CI. Track manual content and consent sign-offs separately from automated results. Do not present a green unit-test run as evidence of Twilio registration or carrier delivery.

## 7. Decisions and external prerequisites still requiring evidence

These are release inputs, with default behavior above so coding can proceed without ambiguity:

- **Sender owner:** church-owned direct account or Rooted as ISV for multiple churches. Follow the [Twilio setup guide](option-b-twilio-setup.md); pilot is one registered church/sender until this is settled.
- **Public-content authorization:** each church owner reviews all live studies before its flag is enabled. If no approval, stay private. No historic member comments are published by default.
- **SMS opt-in wording/evidence:** the sender supplies its actual form/keyword/script, policy URLs and consent records. Unknown or ambiguous consent stays suppressed. [Twilio policy](https://www.twilio.com/en-us/legal/messaging-policy).
- **Comment moderation capacity and removal contact:** church names a moderator and a reachable contact before enabling anonymous comments. If absent, keep comments off while public reading/reactions can proceed.
- **Indexing:** pilot defaults to `noindex`; a later church/product decision may allow indexing. Public access is unaffected.
- **Retention:** determine periods for visitor reaction identifiers, public comments/reports, recipient phones/consent evidence, member legacy data and backups before final contraction. Existing immutable audit/consent records are not deleted by the feature migration.

For implementation, begin with the [master build prompt](../../BuildPrompts/option-b-public-study-migration/MASTER_BUILD_PROMPT.md). This plan deliberately separates code-ready defaults from Twilio registration and church content/consent approvals that must be evidenced before production activation.
