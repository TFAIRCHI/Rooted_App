# Build prompt: church-first invitations and team sign-in

## Objective

Take Rooted from its current subject-first, manually shared invitations to a complete email-first contributor/admin invitation and church-first sign-in journey. Finish code, migrations, real integration checks, release artifacts, and deployment handoff. Do not deploy production or send real invitations to third parties without the owner’s explicit authorization. Follow [the research decision](../../research/church-first-invitations-and-sign-in.md).

## Required user journey

1. A church administrator opens **Settings → Members & access** in a clearly named church and selects **Invite person**. The form asks for first name, last name, email address, and role. Show role capabilities and a confirmation with the church name. Remove **Exact provider subject** and manual token sharing from the normal interface. After submission show Pending, Sending/Sent/Delivery failed, Accepted, Expired, Revoked and Resend as appropriate. Give actionable error text.
2. A recipient receives a branded email identifying Rooted, the inviting church, intended role, expiry, and one safe accept link. The link opens a church-branded invitation preview; no public study reader sign-in is introduced. The recipient signs in or creates their Entra External ID account. If privileged access requires contributor MFA, complete that flow before the grant is active. On success show confirmation and open the selected church’s dashboard.
3. The product’s **Team sign in** path makes church context explicit before credential entry. Accept a church slug/link and support a post-auth chooser when a signed-in person has multiple churches. Preserve the selected church across OIDC state/callback. Verify active membership in that church after authentication and route to it; offer a useful wrong-church/no-access recovery path without disclosing email membership before auth. The workspace header and switcher always show the current church.
4. A person already using Church A can accept a Church B invitation with the same Entra identity and use both from the church picker. A separate account per church is never required.
5. The invitation form uses exactly first name, last name, email address, and role. Team sign-in identifies the church and uses the configured Entra email-based authentication flow.

## Implementation requirements

- Trace and update `frontend/components/settings-members.tsx`, `frontend/components/public/sign-in.tsx`, `frontend/components/public/onboarding.tsx`, `frontend/components/workspace.tsx`, `backend/src/api/onboarding-routes.ts`, `backend/src/auth/routes.ts`, related types, tests, migrations and release docs. Keep the rest of the four Settings views and left navigation intact.
- Review the existing role-capability mapping before exposing roles in the new form; the current contributor grant includes approval and publishing capabilities. Show the actual permissions and apply the approved least-privilege mapping. Keep the audit reason server-generated or in an optional advanced field so the normal invitation form requires only the four requested values.
- Add an additive invitation migration: church ID, normalized destination email, first/last name, role, inviter, hashed random single-use token, expiry, delivery state/attempt metadata, acceptance subject/time, revocation, and audit data as needed. Define uniqueness for a live invitation per church/email and safe resend behavior. Preserve old rows and a bounded compatibility path. Avoid plaintext tokens in database, logs, analytics, or API list responses.
- Implement server-side input validation, email normalization with conservative rules, tenant-scoped queries/RLS, idempotent create/resend, expiry/revocation, rate limits, and generic pre-auth error messages. Check inviter authority again at acceptance, block self-elevation, and protect policy-owner/admin rules. Never allow an invitation to replace an existing member role automatically.
- Add an email delivery adapter with a production provider, verified sender-domain configuration, templates, send result tracking, and retry/reconciliation for uncertain delivery. Use a test transport locally. Keep email credentials server-side. Do not claim “sent” until the provider accepts the send. Document required Azure resources, secrets, DNS/domain verification, monitoring, and cost. No SMS invite fallback.
- Bind acceptance to the authenticated Entra tenant/object identity **and** control of the destination mailbox. Inspect actual production token claims and user flow. If a trustworthy verified-email claim is unavailable, implement a same-browser email challenge delivered to the invited address. A link alone must not let a different provider account claim the role. Preserve verified MFA for contributor/admin access. Store the durable identity subject only after successful binding; never merge existing users by email alone.
- Keep invitation tokens out of server access logs and referrers: use a fragment-based handoff or another reviewed token transport, submit the token to the API over POST, and set a strict referrer policy. Redact tokens and email challenge codes from logs and analytics.
- Carry church context through an opaque, expiring, one-time auth state or validated continuation; do not trust client-supplied church IDs at callback. A selected church cannot expand the authenticated user’s permissions. Avoid open redirects and account/church enumeration. Preserve existing global session and per-church memberships.
- Update the continuation allowlist for the new Settings routes and invitation acceptance destination, with tests for allowed church-scoped paths and rejected external destinations.
- Migrate current subject-first invitations safely: keep existing pending tokens redeemable until expiry, but make new invites email-first. Decide and document whether old endpoints are restricted to migration support or removed after compatibility expires. Ensure a failure to send email leaves an accurate, retryable state and never grants membership.
- Provide accessible, mobile-friendly form, invitation preview, sent/failed state, church selector and multi-church chooser. Include plain wording for a user who already has an Entra account versus one who needs to create one. Keep public link readers out of this flow.

## Acceptance checks

- Unit/integration tests: same email in two churches; two invites to the same church; expired/revoked/replayed link; wrong authenticated identity/email; missing verified email evidence; MFA failure; unprivileged inviter; inviter loses authority; final-admin/self-grant protections; idempotent resend and uncertain provider response; church A cannot read or mutate B’s invitation; direct URL to B without membership denied; safe continuation and open-redirect rejection.
- Browser tests on desktop/mobile: admin creates and resends invitation, sees correct status; recipient accepts into named church; existing account adds a second church; general sign-in chooses the intended church; church switcher works; public study links still read without sign-in; keyboard and screen-reader labels, focus, errors and status announcements work.
- Live pre-release checks with test addresses and the actual Entra customer tenant: verify email/password or email-code sign-up, contributor MFA, stable `oid` across configured clients, email proof, delivery from the verified domain, invitation callback, and repeat sign-in. Record evidence without tokens, codes, or personal email addresses. If live identity or email prerequisites are unavailable, report the exact blocker and keep production rollout gated.
- Run typecheck, lint, relevant integration/browser suites, build both images, inspect architecture and IDs, check migrations against a disposable database, and write a handoff with exact image tags/digests, new secrets, migration order, Portal steps, health checks and rollback. API and frontend must be deployed as a coordinated release; worker only if email delivery/background jobs require it.

## Completion standard

The admin can invite by name/email/role without knowing a provider subject, the recipient can use the emailed link and their verified identity, and team sign-in lands in the church deliberately selected. The same identity can work in multiple churches. No interface claims an email was sent or a role was granted until those actions actually succeed. The result is tested, documented, and ready for the owner’s deployment decision.
